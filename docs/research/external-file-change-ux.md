# External File Change UX

> Research date: 2026-08-27. Sources are limited to official documentation, official repositories, and maintainer-authored issue comments.

## Conclusion for Fuxian

Fuxian should **automatically reload a changed source document**. It is a read-only finished-document reader, so it has no unsaved local buffer to protect. Requiring confirmation for every AI-authored revision would interrupt the primary use case.

Automatic reload should still be visible and position-stable:

- Coalesce bursts of filesystem events and wait until writes settle, keep the current finished document visible, and render the new revision before swapping it in.
- Preserve the nearest visible heading plus its viewport offset; if that heading was removed, fall back to the nearest surviving block and then relative progress.
- Show an ephemeral status beside the filename: `正在更新...` while work is perceptible, then `已更新 · 14:32` for a short period. Repeated writes keep one status active rather than creating notifications.
- If rendering fails, keep the last successful revision visible and show `更新失败，正在显示上一版本`, with retry and details actions.
- Do not automatically jump to appended content. A separate `有新内容` action can appear when the user is reading away from the end.

This status is an original Fuxian recommendation, not a convention established by the products below. It solves awareness without introducing MarkText-style reload decisions.

## Design Implications

The evidence supports separating two policies:

1. **Conflict policy:** Editors must distinguish a clean model from unsaved local edits. Fuxian currently has no dirty state, so silent reload is safe. If editing is introduced later, dirty documents need a compare/keep/overwrite path before this policy can be reused.
2. **Continuity policy:** Reloading content does not imply resetting the reading position. Notepad++ makes this distinction explicit; VS Code applies a diff to an existing model. Fuxian should make semantic-anchor restoration part of the reload contract because rendered Markdown geometry can change substantially when prose or diagrams are inserted above the viewport.

A useful state model is:

`watching -> change detected -> rendering -> updated`

with failure returning to the last successful render rather than a blank or partially rendered document. Fast successful passes may skip the visible `正在更新...` phase to avoid flicker, but the brief completion timestamp still communicates that external work arrived.

MarkText provides direct evidence for a stabilization window: its watcher waits for an open file's write activity to remain stable, polling every 150 ms for up to a 1000 ms stability threshold before processing the change. [watcher constants and loop](https://github.com/marktext/marktext/blob/e52106fd1cdcbd33c1258b7b0cdc7013c4c5d86c/packages/desktop/src/main/filesystem/watcher.ts#L16-L17) [stability check](https://github.com/marktext/marktext/blob/e52106fd1cdcbd33c1258b7b0cdc7013c4c5d86c/packages/desktop/src/main/filesystem/watcher.ts#L231-L243) Fuxian need not copy those exact timings, but it should treat write stabilization as part of correctness, not merely visual debounce.

## Evidence Gaps

- VS Code source establishes reload and dirty-conflict behavior, but not a formal guarantee for scroll or selection after arbitrary external changes.
- Obsidian is closed source; official help confirms automatic refresh but does not expose its clean/dirty decision logic or position behavior.
- Notepad++ documents caret and scroll retention, but not how it behaves when the original location is deleted.
- No reviewed primary source establishes an ephemeral “updating” status as a common desktop pattern; this is a Fuxian-specific response to frequent AI writes.
